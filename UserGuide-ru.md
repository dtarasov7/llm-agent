# Coding Agent 1.2.0 — Руководство пользователя

Руководство описывает поведение, реализованное в `coding_agent.py`. [English version](UserGuide.md) содержит те же разделы и примеры. Краткое введение находится в [README-ru.md](README-ru.md).

Профили Strata настроены по [рекомендациям Qwen3.8-Flash-Next](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF#best-practices): fast — temperature=0.7, top_p=0.80, top_k=20, min_p=0.0, presence_penalty=1.5, repetition_penalty=1.0; deep — temperature=1.0, top_p=0.95, top_k=20, min_p=0.0, presence_penalty=0.0, repetition_penalty=1.0. При переключении профиль заменяет все эти параметры. Допустимы temperature 0..2, top_p >0 и ≤1, top_k — целое 1..64, min_p 0..1, presence_penalty 0..2 и конечный repetition_penalty >0. Для других моделей настройте профили отдельно. Эти настройки не гарантируют устранение циклов; presence_penalty может вызывать смешение языков и снижение качества. balanced использует те же параметры sampling, что и deep. /profile balanced задаёт effort=medium и бюджет рассуждений 2048; /profile deep — effort=high и reasoning_budget_tokens=0 (без отдельного бюджета). Общий max_tokens=8192 включает рассуждения и ответ. Сравнивайте время всей задачи, число исправлений и суммарные токены: короткие ответы могут увеличивать число повторных попыток. Модель может исчерпать общий лимит до формирования вызова инструмента. Агент не меняет reasoning_loop_recovery и YaRN на сервере.

### Ollama

Запуск: `python coding_agent.py --workspace /path/to/project --backend ollama --model YOUR_MODEL`. Адрес по умолчанию http://127.0.0.1:11434; измените BACKENDS для удалённого сервера. Модель должна быть установлена и поддерживать вызовы инструментов. /model показывает доступные идентификаторы.

Профиль fast активен по умолчанию и отключает thinking через reasoning_effort=none. /profile deep сохраняет модель, задаёт low, temperature=0.6, top_p=0.95 и max_tokens=8192. Управление thinking зависит от модели и версии Ollama. /thinking on без заданного effort использует medium; /thinking auto оставляет параметры профиля. Отдельный reasoning-бюджет и top_k через OpenAI-совместимый адаптер не передаются; такие поля профиля отклоняются.

Для статистики рабочего контекста задайте --context-window N: адаптер не считает обучающий предел модели фактическим контекстом Ollama. Этот параметр не меняет настройки сервера. Документация API: [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility).

## 1. Назначение и модель работы

Coding Agent — терминальное приложение для создания кода, адресных изменений, исследования traceback, рефакторинга и обновления тестов. Пользователь вводит задачу на естественном языке; локальная LLM запрашивает небольшой набор проверяемых инструментов. Приложение выполняет правки и возвращает модели фактические результаты.

Три каталога выполняют разные функции:

| Каталог | Назначение |
| --- | --- |
| Исходный проект | Источник из `--workspace`; инструменты модели не могут записывать в него. |
| Рабочая копия агента | Независимая копия сеанса, в которой накапливаются правки. |
| Снимок проверки | Свежая временная копия для изолированной утилиты; изменения обратно не переносятся. |

Завершённая задача означает окончание ограниченного рабочего цикла агента. Изменения ещё не обязательно опубликованы: `/apply` является отдельным действием пользователя. Успех статической проверки доказывает только соответствующий результат синтаксиса или lint.

## 2. Требования и предварительная проверка

Приложение требует Python 3.8+ и не использует сторонние библиотеки Python. Для безопасных проверок проекта дополнительно нужны Linux, непривилегированная учётная запись, доверенный `bwrap` владельца root и доступные непривилегированные пространства имён. Переносимый режим включён по умолчанию и не требует пользовательского менеджера systemd либо делегированных контроллеров cgroup. Для строгого режима дополнительно нужны доверенные `systemd-run`/`systemctl`, доступный менеджер пользователя, cgroups v2 и контроллеры памяти, процессов и CPU. Python должен разрешаться в доверенную системную установку внутри `/usr`; среда из HOME пользователя для безопасных проверок отклоняется.

Сервер должен предоставлять получение моделей и совместимый с OpenAI chat completion со структурированными вызовами инструментов. Настройте сервер отдельно. Агент не устанавливает пакеты и не меняет системное делегирование ресурсов.

Необязательные утилиты должны быть заранее доступны в доверенных системных каталогах. Это относится к Bash, ShellCheck и Ansible. Виртуальная среда проекта по умолчанию исключается из снимков и не монтируется для проверок. pytest должен импортироваться системным Python внутри изоляции.

После запуска выполните `/security`. Статус `ENABLED` требует успешной реальной проверки изоляции; `DEGRADED` означает её недоступность. Правки файлов в отдельной копии остаются возможными, однако `SANDBOX_ERROR` не позволяет агенту объявить результат проверенным. Начальная проверка изоляции не требует запроса LLM.

## 3. Запуск и параметры командной строки

Запустите файл из оболочки:

```bash
python3.8 coding_agent.py --version
python3.8 coding_agent.py --help
python3.8 coding_agent.py --workspace /home/user/projects/demo --backend home-llama --model qwen36-fast
python3.8 coding_agent.py --workspace /home/user/projects/demo --sandbox strict  # необязательный режим cgroup
```

Обычный старт выводит версию `1.2.0`, пути оригинала и копии, состояние сеанса `NEW` или `RESUMED`, сервер, модель, режимы правок и изоляции, предел шагов, каталог состояния и состояние безопасности. При наличии неприменённых изменений автоматически подключается последняя сохранённая совместимая копия; иначе создаётся новая. В восстановленном сеансе загружаются задача и сохранённая модель, поэтому можно сразу выполнить `/apply` с обычным просмотром и подтверждением. `/resume` позволяет вручную подключить задачу без неприменённых изменений.

| Параметр | Значение и настройка по умолчанию |
| --- | --- |
| `--workspace PATH` | Каталог исходного проекта; по умолчанию текущий каталог. |
| `--backend NAME` | Ключ в BACKENDS; доступны home-llama, vllm, strata, ollama. DEFAULT_BACKEND задаёт локальный выбор по умолчанию. |
| `--model NAME` | Явный идентификатор модели сервера; заменяет модель из настройки адаптера. |
| `--context-window TOKENS` | Положительный предел токенов для статистики. |
| `--llm-timeout SECONDS` | Положительный таймаут ожидания сокета HTTP чата; по умолчанию 600 секунд. |
| `--max-tokens N` | Лимит токенов одного ответа, по умолчанию 8192; передаётся серверу как max_tokens. |
| `--no-stream` | Непотоковый режим для несовместимых серверов. |
| `--review` | Начать в REVIEW вместо AUTO. |
| `--new-session` | Создать новую изолированную копию, даже если в прежнем сеансе остались неприменённые правки. |
| `--sandbox portable\|strict` | Политика ресурсов проверок; по умолчанию `portable`, для `strict` нужны пользовательская служба systemd и подтверждённые лимиты cgroup. |
| `--state-dir PATH` | Закрытый каталог состояния; стандартное расположение описано в разделе 16. |
| `--self-test` | Выполнить встроенные тесты без сервера LLM и выйти. |
| `--version` | Вывести имя файла и версию, затем выйти. |
| `--help` | Вывести справку argparse и выйти. |

Пути состояния и исходного проекта не должны пересекаться: ни один не может содержать другой. Например, используйте `/home/user/projects/demo` вместе с `/home/user/.local/state/coding-agent`, но не `demo/.agent-state`. Начальное копирование отклоняет опасные ссылки и специальные файлы и ограничивается настроенными размером и числом объектов.

## 4. Настройка серверов

Измените константы в начале `coding_agent.py`; отдельного конфигурационного файла приложения нет. Замените поставляемые локальные адреса доступными URL. URL может содержать `/v1` либо корень сервера; адаптер добавляет недостающий префикс чата. Учётные данные внутри URL, строки запроса, фрагменты и перенаправления запрещены.

```python
BACKENDS = {
    "home-llama": {
        "type": "llama.cpp",
        "url": "http://127.0.0.1:12345",
        "api_key": None,
        "model": None,
        "context_windows": {"your-fast-model-id": 32768},
    },
    "vllm": {
        "type": "vllm",
        "url": "http://127.0.0.1:8000/v1",
        "api_key_env": "VLLM_API_KEY",
        "model": None,
    },
}
LLM_PROFILES = {
    "strata": {
        "fast": {"model": None, "thinking": "off", "max_tokens": 8192,
                 "temperature": 0.7, "top_p": 0.80, "top_k": 20,
                 "min_p": 0.0, "presence_penalty": 1.5, "repetition_penalty": 1.0},
        "balanced": {"model": None, "thinking": "on", "reasoning_effort": "medium",
                     "reasoning_budget_tokens": 2048, "max_tokens": 8192,
                     "temperature": 1.0, "top_p": 0.95, "top_k": 20,
                     "min_p": 0.0, "presence_penalty": 0.0, "repetition_penalty": 1.0},
        "deep": {"model": None, "thinking": "on", "reasoning_effort": "high",
                 "reasoning_budget_tokens": 0, "max_tokens": 8192,
                 "temperature": 1.0, "top_p": 0.95, "top_k": 20,
                 "min_p": 0.0, "presence_penalty": 0.0, "repetition_penalty": 1.0},
    },
}
```

Заданный `api_key` имеет приоритет над указанной переменной окружения. Предпочитайте `api_key_env` хранению учётных данных в коде. Пример vLLM читает `VLLM_API_KEY` из окружения агента при создании адаптера; проверкам проекта этот ключ API не нужен.

Для llama.cpp используйте `llama-server` с `--jinja` и подходящим шаблоном вызова функций. Псевдонимы моделей и идентификаторы router должны совпадать с выводом `/model`. См. [официальную документацию вызова функций](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md).

Для vLLM настройте `--enable-auto-tool-choice` и совместимый с моделью `--tool-call-parser`; выбор обработчика зависит от модели и версии сервера. См. [документацию инструментов vLLM](https://docs.vllm.ai/en/latest/features/tool_calling/). Операции с файлами и проверки выполняет приложение; настройка API модели не предоставляет серверу доступ к проекту.

### Проектные skills

Каждый навык размещается в `.agents/skills/<имя>/SKILL.md` внутри **целевого проекта**. Навыки копируются в изолированную рабочую копию вместе с проектом; правки исходного каталога не синхронизируются с уже открытым сеансом. `/skills` показывает навыки текущей копии и ошибки обнаружения; `/skills имя` выводит инструкции без запуска задачи. TAB дополняет имена после `/skills`.

Пример `.agents/skills/docstrings/SKILL.md`:

```markdown
---
name: docstrings
description: Добавление кратких docstring функций в стиле проекта.
---
Перед документированием прочитай реализацию функции.
Опиши назначение, типы параметров, результат и реальные условия ошибок.
Сохраняй существующее поведение.
```

Имя каталога должно совпадать с `name`: 1–64 строчные латинские буквы, цифры, дефисы или подчёркивания; первый символ — буква либо цифра. Поле `description` обязательно. Поддерживаются обычные строки YAML, строки в одинарных/двойных кавычках и многострочные описания `>`/`|`. Прочие поля заголовка игнорируются; это не универсальный парсер YAML. Каталог ограничен 50 записями, описания сокращаются до 256 символов. Каждый навык или ресурс ограничен 64 КиБ и 24000 символами; слишком большие или неверно оформленные инструкции сообщаются как ошибки, а не незаметно обрезаются.

В начале задачи в контекст попадают только имена, описания и пути навыков. Модель может обновить каталог через `list_skills` и загрузить подходящий навык через `read_skill(name)`. Для явного выбора известного навыка добавьте `$docstrings` в задание, в том числе в `/edit`: `Используй $docstrings для документирования sort_words.py`. Распознанные упоминания загружают инструкции до первого запроса LLM (не более восьми навыков). Неизвестные слова с долларом остаются обычным текстом задачи. Загруженные инструкции сохраняются в диалоге и восстанавливаются через `/resume`; автоматический выбор зависит от модели.

Вспомогательные текстовые файлы читаются через `read_skill(name, path)`, где `path` задан относительно каталога навыка, например `references/style.md`. Абсолютные пути, переходы к родительским каталогам, символьные и жёсткие ссылки запрещены. Загрузка навыка не запускает его скрипты. Навыки подчиняются задаче пользователя, существующим возможностям инструментов и правилам изоляции. Каталог навыков принадлежит проекту; общие пользовательские каталоги автоматически не просматриваются.

### Сервер Strata

Используйте тип `strata`, чтобы автоматически получать предел контекста выбранной модели и её псевдонимов из `/v1/models` → `meta.n_ctx`. При типе `vllm` чат работал, но предел оставался неизвестным: vLLM использует поле `max_model_len`. Обычные ответы, SSE, `reasoning_content`, `tools`, фрагменты `tool_calls` и usage в завершающем событии покрыты тестами. Инструменты выполняет агент; запросы не включают `strata_mcp`.

Пример конфигурации:

```python
"strata": {"type": "strata", "url": "http://127.0.0.1:8080",
           "api_key_env": "STRATA_API_KEY", "model": "strata"},
```

Задайте фактический ID модели из `/model`; адрес может оканчиваться на `/v1`. `/thinking off` передаёт `chat_template_kwargs.enable_thinking=false`. Без явного переключения действует настройка сервера. `LLM_PROFILES` задаёт `reasoning_effort` и `reasoning_budget_tokens` для профилей сервера; перед использованием сверяйте поддержку с установленной версией. Strata отклоняет запрос, если промпт вместе с лимитом ответа не помещается в контекст: используйте `/compact` заранее или уменьшайте `/max-tokens`.

Источники: [DETAILS.md](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md), [serve/server.py](https://github.com/Niko1221/Strata/blob/main/serve/server.py), [serve/frontend.py](https://github.com/Niko1221/Strata/blob/main/serve/frontend.py). Проверена ветка main 7 октября 2026 года; локальные тесты воспроизводят контракт, но не заменяют проверку конкретной версии сервера. Повторная живая проверка настроенного адреса прошла 7 октября 2026 года: qwen3.8-flash-next-iq3_xxs, n_ctx=131072; проверены потоковые ответы, корректный вызов инструмента без исполнения и управление reasoning. Responses API, Anthropic Messages и серверные MCP-инструменты в этом адаптере не используются.

### Управление reasoning в Strata

Для Strata используйте /profile fast без рассуждений, /profile balanced для medium с бюджетом 2048 токенов и /profile deep для high без отдельного бюджета. Все три профиля ограничивают полный ответ 8192 токенами. /thinking off временно отключает reasoning; /thinking on включает его с параметрами текущего профиля; /thinking auto убирает переключатель агента, сохраняя параметры профиля и настройки сервера. Ручные изменения отмечаются в /profile как modified. Положительный reasoning_budget_tokens ограничивает рассуждения, а 0 означает отсутствие отдельного бюджета. Уровни effort и бюджет задаются в LLM_PROFILES; отдельные команды для них не предусмотрены.

В Strata по умолчанию выбран fast. Для обычных правок рекомендуем его сохранять: ранее длительные рассуждения исчерпывали бюджет ответа. Deep — стартовая настройка для сложного анализа, не измеренный оптимум. Рассуждения и завершающая вставка сервера входят в общий лимит max_tokens. Без переопределений сервер использует high. Живые проверки подтвердили off, low и срабатывание отдельного бюджета.

## 5. Модели, профили и thinking

```text
/model
/model your-fast-model-id
/profile fast
/profile deep
/thinking auto
```

`/model` показывает текущую модель, запрашивает доступные идентификаторы и обновляет подсказки дополнения. `/model NAME` сразу выбирает идентификатор; его доступность определяется следующим запросом к серверу. Если модель не настроена и обнаружена ровно одна, новая задача выбирает её автоматически; иначе укажите модель явно. Отдельная константа `DEFAULT_MODEL` не используется как запасной выбор: задавайте поле `model` адаптера либо `--model`.

`/profile` показывает профили текущего backend, текущую модель, фактические параметры и признак modified. /profile fast и /profile deep применяют полный набор настроек генерации, удаляя прежние параметры; LLM_PARAMETERS используется только до выбора профиля. Для Strata fast активен при запуске. /model, /thinking и /max-tokens переопределяют профиль и отмечают его изменённым до повторного применения. model=None сохраняет модель; если она не выбрана, агент выбирает единственную доступную либо требует /model NAME. Явный ID проверяется по списку моделей до изменения настроек. Неподдерживаемые поля и параметры отклоняются. По умолчанию effort разрешён для Strata и Ollama, отдельный reasoning-бюджет — только для Strata; для другого сервера поддержка должна быть явно указана в BACKENDS через profile_capabilities после проверки его API. Диалог и изменения файлов сохраняются. Профили действуют в текущем сеансе; /resume восстанавливает переписку, но не профиль предыдущего запуска.

`/thinking auto` оставляет настройки сервера. `on` либо `off` передаёт `chat_template_kwargs.enable_thinking`. Сервер и шаблон модели должны поддерживать этот параметр; команда сама не реализует рассуждение.

## 6. Ввод, история и автодополнение

Первый текст начинает задачу. Следующие сообщения, в том числе из `/edit`, продолжают тот же диалог с предыдущими ответами, инструкциями и результатами инструментов. Например, после анализа можно написать «сохрани предыдущий анализ в report.md»: модель получает сам предыдущий ответ. `/new` очищает диалог для отдельной задачи. `/continue` продолжает выполнение без нового пользовательского задания. Строка с `/` в начале является командой. Новое сообщение получает бюджет `/continue-steps`, а первая задача — `/max-steps`. В интерактивном терминале с поддержкой bracketed paste вставьте многострочную задачу и один раз нажмите Enter после вставки. Вставленные переводы строк останутся частью одной задачи; Enter вне вставки отправит её.

| Клавиша | Поведение в интерактивном терминале readline |
| --- | --- |
| Вверх / вниз | Предыдущая / следующая запись истории. |
| Влево / вправо | Перемещение курсора в набираемой строке. |
| Home / End | Начало / конец строки. |
| TAB | Дополнение команды или поддерживаемого аргумента; вывод вариантов при неоднозначности. |
| Ctrl+C во время ввода | Отмена строки и возврат к приглашению. |
| Ctrl+C во время задачи | Отмена текущей итерации; проверьте изменения до продолжения. |
| Конец ввода, обычно Ctrl+D | Завершение цикла ввода. |

История содержит введённые команды и задачи, включая многострочные вставки, хранит до `HISTORY_LENGTH = 500` записей и атомарно сохраняется для каждого исходного проекта в закрытом состоянии. Последовательные одинаковые записи повторно не добавляются. История и сохранённые сообщения задачи являются локальными записями пользовательского ввода.

Дополняются команды с `/`, темы справки, режимы, профили, значения thinking, известные и настроенные модели, каталоги для `/files` и имена проверок для `/check`. `/model` обновляет идентификаторы сервера. Дополнение файлов-целей `/check` не реализовано; вводите их явно. Цели с пробелами допускают кавычки, например `/check bash_syntax "scripts/backup copy"`. `/files` получает весь остаток строки напрямую: используйте `/files directory with spaces` без кавычек оболочки.

Если stdin/stdout не являются терминалами либо отсутствует `readline`, остаётся обычный ввод, но редактирование readline, дополнение и постоянная интерактивная история не работают. Для многострочной вставки нужны GNU Readline и терминал с поддержкой bracketed paste.

### Многострочный редактор задачи

Команда `/edit` открывает модальное окно в нижней половине терминала. Рамка нарисована линиями, заголовок расположен по центру верхней рамки, подсказка — на нижней рамке. Нужны интерактивный терминал и стандартный модуль Python `curses`. До отправки текст можно свободно редактировать; текст с `/` внутри редактора является текстом задачи, а не командой REPL. После Alt+Enter полный текст задачи выводится в терминал перед началом работы LLM.

| Клавиша | Действие в редакторе |
| --- | --- |
| Enter | Добавляет новую строку и продолжает редактирование. |
| Влево / вправо / вверх / вниз | Перемещают курсор по тексту и между строками. |
| Home / End | Начало / конец текущей строки. |
| Page Up / Page Down | Перемещают на десять строк вверх / вниз с прокруткой области просмотра. |
| Backspace / Delete | Удаляют перед / после курсора; на границе объединяют строки. |
| TAB | Вставляет табуляцию, отображаемую с шагом четыре позиции. |
| Сочетание вставки терминала, например Ctrl+Shift+V | Вставляет текст буфера в позиции курсора; многострочная bracketed paste вставляется буквально. |
| Ctrl+P / Ctrl+N | Предыдущая / следующая запись истории редактора. Возврат к самой новой позиции восстанавливает новый черновик. |
| Alt+Enter | Закрывает окно и запускает всю задачу; пустой текст не запускается. |
| Esc, затем ещё раз Esc | Закрывает окно без исполнения задачи. |

Непустой текст сохраняется и при отправке, и при отмене. История редактора отделена от истории команд, хранит до `HISTORY_LENGTH = 500` записей для каждого исходного проекта и переживает перезапуск. Последовательные одинаковые тексты не повторяются. При просмотре истории правки и положение курсора сохраняются на время открытого окна. Отменённый черновик можно вернуть через `/edit`, затем Ctrl+P. Отмена ввода по Ctrl+C также сохраняет непустой текст.

## 7. Справочник команд

Точное имя имеет приоритет. Остальные имена можно сокращать до любого уникального префикса; неоднозначный префикс возвращает кандидатов. Например, `/sec` означает `/security`, а `/mo` и `/mod` неоднозначны между `/model` и `/mode`.

| Команда | Поведение |
| --- | --- |
| `/help [tools]` | Список команд либо инструментов модели; включает разрешённые проверки. |
| `/skills [ИМЯ]` | Каталог навыков проекта либо просмотр `SKILL.md`; `$имя` в задаче явно выбирает навык. |
| `/edit` | Многострочный редактор задачи с постоянной историей отправленных и отменённых черновиков. |
| `/tools` | Быстрая справка об инструментах и проверках. |
| `/new` | Очищает контекст задачи, сохраняя изменения файлов сеанса. |
| `/task` | Показывает идентификатор и статус, счётчики, изменённые пути и записанные проверки. |
| `/model [NAME]` | Выводит модели либо выбирает идентификатор. |
| `/profile [fast\|deep]` | Показывает соответствие профилей либо выбирает профиль. |
| `/mode [auto\|review]` | Показывает либо меняет подтверждение отдельных правок. |
| `/files [PATH]` | Выводит один безопасный каталог рабочей копии. |
| `/changes` | Выводит изменения сеанса относительно начальной базы. |
| `/diff [--session] [PATH]` | Показывает изменения текущей задачи; с `--session` — всего сеанса. Принимает относительный путь и абсолютный путь внутри копии агента. |
| `/revert` | Немедленно восстанавливает всю копию до начальной базы сеанса. |
| `/context` | Показывает счётчики диалога и статистику токенов и контекста. |
| `/compact` | Сжать текущий диалог, сохранив инструкции и архив. |
| `/continue` | Выделяет текущей задаче дополнительный ограниченный бюджет итераций. |
| `/thinking [auto\|on\|off]` | Показывает либо меняет необязательный параметр шаблона. |
| `/max-tokens [N]` | Показать или изменить лимит ответа без перезапуска. |
| `/resume` | Вручную загружает последнюю совместимую задачу и сеанс; ещё не выполняет их. |
| `/apply` | Показывает неприменённые файлы и числа изменённых строк, подтверждает, копирует и переносит файлы. |
| `/discard` | Подтверждает неприменённые изменения при их наличии, удаляет копию и выходит. |
| `/security` | Обновляет проверку изоляции; показывает лимиты, причины отказа и утилиты. |
| `/check [NAME TARGET ...]` | Выполняет разрешённую проверку с необязательными относительными целями. |
| `/quit` | Выходит; сохраняет рабочую копию и состояние. |

`/task`, `/context`, `/compact` и `/continue` требуют текущей задачи. `/check` при необходимости создаёт задачу ручной проверки и по умолчанию выбирает `python_compile`. `/apply` и `/discard` работают с изолированным сеансом независимо от задачи модели. Модель не может вызывать команды переноса как инструменты.

Один запуск задачи по умолчанию ограничен 500 обращениями к LLM, а /continue разрешает ещё 500. Это отдельный лимит шагов, не лимит токенов или контекста. Остановки по лимитам и отмены выделяются жирным жёлтым, ошибки задачи — жирным красным. При перенаправлении вывода, TERM=dumb или наличии NO_COLOR ANSI-цвета отключены; текстовые метки сохраняются.

Лимиты задаются параметрами запуска `--max-steps N` и `--continue-steps N`. В текущем сеансе команды `/max-steps [N]` и `/continue-steps [N]` показывают или меняют их. Допустимы только положительные целые числа. Настройки действуют до выхода; первый лимит применяется к новой задаче, второй — к следующему уточнению или /continue.

Команды распознаются и в русской раскладке: `.й` → `/q`, `.рудз` → `/help`, `/вшаа кщдуы.тпштч` → `/diff roles/nginx`. Аргументы в русской раскладке также исправляются; например, /thinking щаа превращается в /thinking off. Уже английские аргументы сохраняются, регистр букв в путях учитывается. Для точки вместо / исправление выполняется только при совпадении имени или префикса существующей команды; неоднозначные сокращения по-прежнему требуют уточнения.

Диалог сохраняется и после завершения задачи. `/diff` и статистика относятся ко всему текущему диалогу до `/new`; уточнение не сбрасывает исходные версии файлов и результаты проверок. После перезапуска используйте `/resume` для восстановления переписки. Если старая версия уже заменила задачу, `/resume` загружает последнюю сохранённую задачу, а не автоматически объединяет прежние диалоги.

## 8. Правки, review, перенос и восстановление

Обычный рабочий сценарий:

```text
/security
/mode review
Добавь параметр --timeout в backup.py; по умолчанию 30 секунд; обнови тесты.
/task
/diff
/check python_compile backup.py
/check unittest tests
/apply
```

В AUTO разрешённые правки сразу записываются в рабочую копию. В REVIEW каждое создание или изменение показывает различия и запрос `Apply change? [y/N]`; только `y` подтверждает запись. Модель получает фактический отказ от отклонённой правки. Оба режима по-прежнему требуют явного подтверждения `/apply` для оригинала.

`/apply` сравнивает неприменённые файлы с последними применёнными суммами источника. Отклоняются неподдерживаемое удаление, опасные пути, существующие цели для новых файлов и внешние изменения оригинала. Команда показывает каждый файл с числом добавленных и удалённых строк относительно **текущего оригинала**, спрашивает `Confirm action? [y/N]`, повторно проверяет конфликты, создаёт резервные копии и журнал намерений, затем атомарно публикует каждый файл. Полный diff не выводится; при необходимости вызовите `/diff` отдельно.

Перенос атомарен для отдельного файла, но не является транзакцией всего проекта. При ошибке в середине сообщения перечисляют уже перенесённые пути и каталог копий. Изучите `apply.json` и резервные файлы до выбора восстановления; автоматического отката оригинала нет.

После каждой задачи терминал показывает пути её файлов и число добавленных и удалённых строк (`+N -M`) относительно состояния перед началом задачи. Замена строки считается удалением и добавлением. Полный diff автоматически не выводится. `/diff` сравнивает файлы с их состоянием до текущей задачи, в том числе если файл создан в более ранней задаче; `/diff path/to/file.py` оставляет один файл задачи. `/diff --session [PATH]` сравнивает с началом всего сеанса. Можно вставить и показанный абсолютный путь файла рабочей копии; путь с пробелами требуется заключить в кавычки. `/changes` показывает изменения всего сеанса, поэтому уже применённые правки могут по-прежнему отображаться там и в `/diff --session`. Повторный `/apply` без новых изменений выводит `No unapplied changes.`

`/revert` не запрашивает подтверждение. Восстанавливается **вся копия сеанса**, включая правки предыдущих задач этого сеанса, до начального состояния. Уже изменённый оригинал остаётся изменённым. Поэтому последующий `/apply` может предложить возврат оригинала к исходному содержимому; сравните оригинал и рабочую копию перед подтверждением. `/new` очищает только контекст и не отменяет правки.

`/discard` удаляет рабочую часть, базу и манифест сеанса после необходимого подтверждения неприменённых изменений, затем выходит. `/quit` сохраняет копию. Удалённый сеанс нельзя восстановить через `/resume`.

## 9. Инструменты модели

| Инструмент | Входы и результат |
| --- | --- |
| `list_files` | Относительный `path`, необязательный `recursive`; объекты и число пропусков. |
| `read_file` | Относительный файл, включительные `start_line`/`end_line` начиная с 1; строки UTF-8 с номерами. |
| `search_text` | Шаблон, относительный путь, маска файлов, флаги regex/регистра, предел; совпавшие пути, строки и текст. |
| `create_file` | Новый относительный путь и текст; существующий файл отклоняется. |
| `edit_file` | Относительный путь, точный `old_text`, замена `new_text`; требуется ровно одно совпадение. |
| `run_check` | Разрешённое имя, относительные цели, ограниченное время; реальный структурированный результат. |
| `get_diff` | Без аргументов; различия текущей задачи. |
| `list_skills` | Без аргументов; ограниченный каталог с именами, описаниями, путями и ошибками обнаружения. |
| `read_skill` | Обязательное `name`, необязательное `path` (по умолчанию `SKILL.md`); чтение навыка либо его текстового ресурса. |

Неизвестные инструменты и аргументы запрещены. Модели не предоставляются произвольная команда, исполняемый файл, строка shell, установка пакетов или сетевой инструмент. `AGENTS.md` проекта читается при старте задачи, однако не расширяет полномочия. Prompt требует изучать нужные файлы до редактирования и делать адресные замены.

Пути должны быть относительными. Запрещены абсолютные/UNC/дисковые пути, `..`, `.git`, альтернативные потоки, symlink и reparse points; чтение текста также отклоняет hard links, двоичные нулевые байты, неверный UTF-8 и слишком большие файлы. Новые файлы используют UTF-8/LF; существующие BOM UTF-8 и единообразные CRLF сохраняются при правке.

Поиск подстроки выполняется в приложении. Совпадения regex ищет изолированный обработчик с пределом три секунды; недоступная изоляция делает поиск regex недоступным. Для больших файлов указывайте диапазон строк. Ход инструментов содержит имена файлов, диапазоны и проверки, цели, предел времени, фактическую длительность и статус.

## 10. Проверки Python

```text
/check python_compile backup.py src/config.py
/check unittest tests
/check pytest tests/test_backup.py
```

`python_compile` запускает системный Python с `-I -m py_compile` для файлов `.py`. Это не доказывает корректность выполнения. По умолчанию модель проверяет изменённые файлы Python. Если ручной `/check python_compile` не содержит целей и изменённых Python-файлов нет, CLI перечисляет Python-файлы рабочей копии.

`unittest` выполняет discovery не более чем в одном каталоге. Без цели используется `tests`, если он существует, иначе стандартный поиск в рабочем каталоге. Отчёт с нулём обнаруженных тестов получает `FAIL`, даже если процесс вернул ноль.

`pytest` использует модуль pytest системного Python. Если модуль не установлен в видимой среде, сохраняется реальная диагностика; автоматической установки и перехода к виртуальной среде проекта нет.

Проверка завершения требует компиляции изменённых файлов Python и выполнения тестов при наличии тестовых файлов или каталогов. Фактические ошибки нужно исследовать и перепроверять в бюджете задачи. Импорт и выполнение тестов происходят в временных снимках.

## 11. Проверки Bash

```text
/check bash_syntax scripts/backup.sh bin/deploy
/check shellcheck scripts/backup.sh bin/deploy
```

`bash_syntax` отдельно запускает доверенный `bash -n` для каждого файла, сохраняя его статус, код завершения и вывод. Явные цели могут иметь любое расширение. Автовыбор учитывает `.sh` и shebang Bash: `#!/bin/bash`, `#!/usr/bin/bash`, `#!/usr/bin/env bash`. Для файла `#!/bin/sh` рекомендуется ShellCheck; проверка Bash не выдаётся за проверку POSIX.

Используйте ShellCheck после успешной проверки синтаксиса Bash. Фиксированная команда запрещает загрузку rc и не включает `-x`; диагностика сохраняет номера строк и идентификаторы вроде `SC2086`. Контроль внешних source соответствует [документированному ограничению ShellCheck](https://www.shellcheck.net/wiki/SC1144). Файлы source автоматически не обходятся при этой политике.

Отсутствие доверенных Bash/ShellCheck даёт `SKIPPED`; диагностика утилиты — `FAIL`; ошибка создания изоляции — `SANDBOX_ERROR`. Результаты относятся только к статическому синтаксису и анализу. Приложение не выполняет скрипты функционально и не предоставляет Bats или `bash_run`.

## 12. Проверки Ansible

```text
/check ansible_syntax site.yml playbooks/upgrade.yml
/check ansible_syntax roles/nginx
/check ansible_lint roles/nginx
/check ansible_lint .
```

`ansible_syntax` вызывает `ansible-playbook --syntax-check` отдельно для каждого распознанного playbook либо роли. Роли распознаются по каталогам `tasks`, `handlers`, `defaults`, `vars`, `templates`, `files` или `meta`. Файл `roles/nginx/tasks/main.yml` сопоставляется с `roles/nginx` и не считается отдельным playbook. Произвольный YAML, например OpenAPI или CI-конфигурация, не выбирается автоматически, если его путь или содержимое не соответствуют эвристике playbook.

Доверенная подготовка создаёт монтирование `/sandbox` только для чтения вне дерева проекта снимка. Сгенерированный inventory:

```ini
[agent_test]
localhost ansible_connection=local
```

`ANSIBLE_CONFIG` указывает на `/sandbox/ansible.cfg`, а команда синтаксиса явно выбирает `/sandbox/inventory`. Конфигурация задаёт один fork, включённую проверку ключей хостов, отключённые retry files и пути ролей и коллекций внутри проекта. Для роли создаётся playbook с `hosts: agent_test`, `gather_facts: false` и безопасно заключённым в кавычки именем роли. Wrapper не появляется в рабочей копии агента.

Проверки Ansible не используют production inventory проекта, его `ansible.cfg`, конфигурацию HOME хоста, сокеты SSH-agent или секреты vault/Ansible хоста. Плагины и коллекции проекта могут выполнять недоверенный код при проверке; они остаются внутри той же изоляции. Секрет для раскрытия зашифрованной зависимости не запрашивается; отсутствие зависимостей или ключей сохраняется в фактической диагностике.

`ansible_lint` принимает распознанные playbook и проверенные каталоги роли, ролей или проекта. Применяются сгенерированная конфигурация lint и фиксированный `--offline`; [автономный режим](https://docs.ansible.com/projects/lint/configuring/) отключает установку requirements и обновление схем. Сеть остаётся недоступной. Отсутствующая установленная утилита lint даёт `SKIPPED`; отсутствующие зависимости после запуска проверки обычно дают `FAIL` с исходными сообщениями и идентификаторами правил.

После правки Ansible рекомендуется сначала синтаксис, затем lint. Приложение не реализует обычный запуск playbook, `--check`, реальный converge, идемпотентность, Molecule, контейнеры или SSH-цели. PASS синтаксиса/lint нельзя описывать как успешное развёртывание.

## 13. Результаты проверок и статусы задач

| Статус проверки | Значение |
| --- | --- |
| `PASS` | Изолированная утилита успешно выполнилась. |
| `FAIL` | Запущенная проверка вернула ошибку либо обнаружено превышение ресурсов/роста снимка. |
| `SKIPPED` | Внешняя статическая утилита не найдена в доверенном системном каталоге. |
| `TIMEOUT` | Превышено время и подтверждена остановка дочерних процессов. |
| `SANDBOX_ERROR` | Защита или запуск недоступны либо остановка не подтверждена; проверенного результата нет. |
| `INVALID_TARGET` | Цель статической проверки опасна, отсутствует либо не распознана; утилита не запускалась. |

Обычные ошибки целей Python могут возвращаться как `TOOL_ERROR`, а не как `INVALID_TARGET` статических проверок. Ни один статус не означает PASS. Ошибка ресурсов может добавлять `resource_limit` и счётчики событий cgroup. При неподтверждённой остановке `SANDBOX_ERROR` сообщает карантин вместо утверждения об очистке.

Записанный результат включает имя, статус, код завершения, длительность, stdout/stderr, цели, ревизию задачи, данные времени/ресурсов и метаданные изоляции. Общий статический результат содержит `files`, `sandboxed` и сообщение о статическом характере. Синтаксические проверки нескольких целей используют отдельные снимки; ошибка инфраструктуры или времени останавливает оставшиеся запуски. Большая диагностика сохраняет начало и конец. `/task` показывает записанные статусы; `/check` выводит структуру результата.

Статусы задач: `ACTIVE`, `COMPLETED`, `LIMIT`, `BLOCKED`, `CANCELLED`, `ERROR`, `REVERTED`. `BLOCKED` означает отказ изоляции текущей ревизии. `LIMIT` допускает `/continue`; `REVERTED` требует новой задачи. Пропущенная необязательная утилита сообщается явно и не включается в утверждение «все проверки прошли».

## 14. Токены и заполнение контекста

Перед каждым запросом чата агент показывает номер ожидаемого ответа, модель, таймаут HTTP и краткую суть: исходную задачу для первого запроса, названия и пути последних инструментов или цели проверок для последующих, либо указание на продолжение/проверку. Перечисляются не более трёх последних инструментов. Это описание метаданных запроса, а не размышления модели. В этих строках нет системного промпта, старой переписки и тел результатов инструментов. После ответа выводится прошедшее время. Сам запрос серверу по-прежнему содержит необходимый для задачи диалог.

Чат по умолчанию использует поток SSE. Каждые 5 секунд индикатор показывает время ожидания, число событий и символов, включая полученные рассуждения; сами рассуждения и текст ответа не печатаются. Это не счётчик токенов: точный расход берётся из итогового usage, если сервер его прислал. `--llm-timeout` (600 секунд) ограничивает ожидание сокета, а не суммарное время активного потока. Для серверов без поддержки SSE или `stream_options` используйте `--no-stream`; автоматического повторного запроса нет. Если сервер вместо SSE вернул обычный JSON, он также принимается. Ошибка или обрыв потока не выполняют частично полученные инструменты. Для продолжения используйте `/continue`, после перезапуска — `/resume`, затем `/continue`.

После каждого ответа выводятся входные, выходные и суммарные токены сервера, а также накопленные значения задачи. Отсутствующие данные обозначаются `n/a`; частичные суммы показывают число ответов с соответствующим счётчиком. Значения включают повторные токены prompt при нескольких запросах и не являются денежным счётом.

`/context` дополнительно показывает число сообщений, шагов, инструментов и файлов и оценку следующего запроса: объём JSON UTF-8, включая определения инструментов, делённый на четыре. Это не измерение токенизатором; результат может заметно различаться для языков и шаблонов чата.

Приоритет предела контекста: `--context-window`, `context_windows` выбранной модели, `context_window` адаптера, затем кешированные метаданные сервера. llama.cpp читает `/props`, совместимые метаданные моделей могут содержать `max_model_len`. При известном пределе выводятся процент и остаток токенов; иначе указывается неизвестный предел.

Статистика не обрезает и не сворачивает диалог автоматически. При исчерпании контекста завершите или сохраните работу, изучите различия и выполните `/new` для новой задачи. Изменения файлов остаются в копии сеанса.

Диагностика LLM отдельно показывает число полученных символов рассуждений, текста ответа и аргументов инструментов (не токенов). Во время потока и при завершении, обрыве или отмене выводятся имена начатых вызовов, включая неполные имена; их содержимое не печатается. Идентификаторы вызовов не входят в счётчики. Нулевой счётчик рассуждений означает, что отдельные поля reasoning/reasoning_content не получены: если сервер смешивает рассуждения с content, они учитываются как текст. Для обычного JSON эти сведения доступны только после получения ответа. Начатый вызов не означает выполненный инструмент.

### Длинные и обрезанные ответы

Лимит одного ответа — 8192 токена. Он задаётся через `--max-tokens N` или `/max-tokens N` и имеет приоритет над `LLM_PARAMETERS["max_tokens"]`. Агент просит модель создавать один-два небольших файла за шаг. Ограничение фактически обеспечивает сервер; для некоторых моделей бюджет также расходуется на рассуждения.

При `finish_reason=length`, другой неподдерживаемой причине завершения или пустом ответе агент переходит в `LIMIT`: частичный ответ не попадает в переписку, инструменты не выполняются, автоматического повтора нет. Перед выполнением проверяется JSON аргументов всего набора вызовов. При необходимости задайте `/max-tokens 8192`, отключите рассуждения через `/thinking off` (требует поддержки шаблона сервера), затем `/continue`. Большая задача должна выполняться несколькими шагами. Эти настройки применяются и к `/compact`, который отклоняет обрезанное резюме. Требование skill запустить недоступный `molecule test` не расширяет возможности агента: он создаёт сценарии, но сообщает, что функциональная проверка не выполнена.

При некорректном JSON аргументов агент отклоняет весь набор инструментов ответа и останавливается без автоматического повтора. Диагностика показывает номер и имя вызова, размер аргументов и позицию ошибки, без содержимого файлов. Расход токенов выводится и для такого ответа; строка получения ответа включает finish_reason. Через /continue модель получает сохранённую инструкцию отправить один небольшой вызов с корректным JSON и минимальным блоком old_text/new_text. Предыдущие изменения файлов сохраняются. Незакрытая строка сама по себе не доказывает достижение лимита токенов: смотрите finish_reason.

### Сжатие контекста и инструкции проекта

При запуске задачи агент сообщает `AGENTS.md загружен: <путь>`, если файл найден в корне изолированной копии. `/context` показывает, загружены ли инструкции, их путь, количество сообщений с каталогом и инструкциями skills, число сжатий и путь последнего архива. Это сведения о сохранённых инструкциях текущей задачи: изменение файла на диске не обновляет их автоматически.

Выполните `/compact`, чтобы получить резюме текущей переписки от выбранной LLM. Агент просит сохранить цель, изменённые файлы, неудачную команду, текущую гипотезу, результаты проверок и следующую точную команду, учитывая раздел `Compact Instructions` из `AGENTS.md`. Качество резюме зависит от модели.

Системный промпт, инструкции проекта, каталог skills, явно подключённые навыки и успешно прочитанные через `read_skill` ресурсы сохраняются целиком. Исходная цель и фактическое состояние задачи добавляются к резюме. Изменения файлов, резервные копии и проверки не сбрасываются. Полная переписка до сжатия сохраняется в `backups/<task-id>/conversation-<uuid>.json` внутри каталога состояния; путь выводится на экран. Архив не отправляется в последующих запросах.

Команда не выполняет инструменты и не продолжает задачу автоматически. После сжатия используйте `/context` для оценки размера и `/continue` для продолжения; `/resume` восстанавливает сохранённое резюме после перезапуска. Расход токенов запроса сжатия учитывается в статистике. Размер до и после показывается в байтах JSON UTF-8, а не в токенах; последнее фактическое число входных токенов относится к запросу сжатия, оценка следующего запроса — к новому контексту.

При ошибке LLM, пустом или обрезанном ответе переписка не заменяется. Если резюме не уменьшает размер, исходный контекст также остаётся. Сжатие само требует запроса с текущей перепиской, поэтому запускайте его до исчерпания окна контекста. Обычная фраза «Сожми контекст» передаётся модели в текущем диалоге; для реального сжатия нужна именно `/compact`.

## 15. Границы безопасности и настраиваемые лимиты

Каждая проверка проекта, включая статический анализ и обработчики regex, проходит через `SandboxRunner`. Проверяются условия выбранного режима, создаётся временный снимок, включается `no_new_privs`, затем создаются пространства имён bubblewrap. Переносимый режим напрямую запускает доверенную проверку Python с лимитами отдельного процесса: `RLIMIT_AS`, `RLIMIT_CPU`, открытых файлов, размера файла и core. Строгий режим создаёт службу systemd пользователя с очищенным окружением и сверяет фактические лимиты cgroup для памяти, swap, процессов и CPU до запуска bubblewrap. Видимы только временный проект, безопасные системные монтирования, закрытые HOME/tmp и созданные метаданные. Сеть проверки отключена; HTTP-запросы серверу модели являются отдельной операцией приложения.

В переносимом режиме проверка является PID 1 в отдельном пространстве процессов: её выход завершает оставшихся потомков. По таймауту останавливается группа bubblewrap; до удаления снимка приложение ожидает закрытия запуска и каналов вывода. Строгий режим останавливает всю cgroup службы и подтверждает её пустоту. Если остановка не подтверждена, каталог запуска помещается в карантин и указывается в результате. Лимиты отдельных процессов переносимого режима не ограничивают общую память, нагрузку CPU и число процессов. Закрытый `/tmp` не имеет отдельной жёсткой квоты в bubblewrap 0.6.3. Не удаляйте карантинные файлы, пока их могут использовать процессы.

| Константа | Значение по умолчанию и действие |
| --- | --- |
| `HTTP_TIMEOUT` | 120 с ожидания сокета для списка моделей и прочих обычных HTTP-запросов. |
| `LLM_TIMEOUT` | 600 с ожидания сокета для запросов чата; заменяется `--llm-timeout`. |
| `MAX_AGENT_STEPS` / `CONTINUE_STEPS` | 500 / 500; --max-steps, --continue-steps и команды сеанса. |
| `MAX_TOOL_CALLS` / `REPEAT_THRESHOLD` | 100 вызовов в бюджете запуска / 5 одинаковых повторов. |
| `CHECK_TIMEOUT` / `SANDBOX_WALL_TIMEOUT` | 120 с; переданный предел проверки ограничивается. |
| `STATIC_CHECK_TIMEOUT` | Не более 60 с на статический процесс. |
| `MAX_FILE_BYTES` / `MAX_READ_BYTES` | 10 МиБ файл / 1 МиБ выбранное чтение. |
| `MAX_LIST_RESULTS` / `MAX_SEARCH_RESULTS` | 1000 объектов / 200 совпадений. |
| `MAX_TOOL_OUTPUT_CHARS` / `STATIC_CHECK_OUTPUT_MAX_CHARS` | 30000; ограниченные начало и конец вывода. |
| `MAX_WORKSPACE_BYTES` / `MAX_WORKSPACE_ENTRIES` | 512 МиБ копируемых данных / 100000 объектов. |
| `SANDBOX_MEMORY_MAX_MB` / `SANDBOX_TASKS_MAX` | 2048 МиБ адресного пространства одного процесса в переносимом режиме; в строгом 2048 МиБ общей памяти, 64 процесса и отключённый swap. |
| `SANDBOX_CPU_QUOTA_PERCENT` | Общая квота CPU 200 процентов только в строгом режиме; в переносимом процессорное время отдельного процесса ограничено таймаутом проверки плюс две секунды. |
| `SANDBOX_OPEN_FILES_MAX` / `SANDBOX_FILE_SIZE_MAX_MB` | 256 открытых файлов / предел отдельного файла 256 МиБ. |
| `SANDBOX_SNAPSHOT_MAX_MB` | Отслеживаемый порог снимка проекта 1024 МиБ; отдельной жёсткой квоты закрытого `/tmp` нет. |
| `SANDBOX_CORE_DUMPS` | False; запуск задаёт нулевой предел core. |
| `HISTORY_LENGTH` / `REGEX_TIMEOUT` | 500 строк истории / 3 с изолированного поиска regex. |

Лимиты задаются константами кода, а не произвольными параметрами модели. Статические проверки используют выбранный режим изоляции. `SANDBOX_ENV_ALLOWLIST` по умолчанию пуст; его изменение может передать выбранные значения хоста проверкам, кроме Ansible. Для Ansible по-прежнему применяется контролируемая фильтрация. `ALLOW_UNSANDBOXED_CHECKS = False` остаётся защитой от запуска без изоляции.

`IGNORE_PATTERNS` исключает `.git`, кеши Python, обычные виртуальные среды, `node_modules` и каталоги редакторов из копий и просмотра. Это не общий фильтр секретных файлов: прочитанный текст проекта может передаваться настроенной LLM. Выбирайте проект и сервер с учётом этого поведения.

Защита файлов предполагает отсутствие враждебного процесса хоста с тем же UID, создающего гонки операций. Контроль роста снимка не является жёсткой квотой диска. Инструменты модели не предоставляют удаление, произвольный shell, установку пакетов или изменения Git. Перенос ограничен командой пользователя.

## 16. Состояние, сохранение и восстановление

В Linux стандартное состояние находится в `${XDG_STATE_HOME:-~/.local/state}/coding-agent`; в Windows путь выбирается из `LOCALAPPDATA` либо `~/AppData/Local`. Сами безопасные проверки требуют Linux. Новые каталоги состояния, запусков и сеансов создаются с закрытыми правами. Состояние — обычные JSON и файлы, без шифрования.

```text
state/
  coding-agent.log
  current-task.json
  history-<original-project-hash>.json
  editor-history-<original-project-hash>.json
  backups/<task-id>/
    task.json
    <path-hash>.original
  workspaces/<session-id>/
    session.json
    baseline/
    project/
  apply-backups/<apply-id>/
    apply.json
    <path-hash>
  runs/check-<id>/
    workspace/
    sandbox/           # Только проверки Ansible
    started
    cgroup.json        # Если проверка ресурсов записала его
```

Обычные каталоги запусков удаляются; оставаться должны лишь активные или карантинные. Копии задачи и копии переноса хранятся отдельно. Ротация журнала использует порог 2 МиБ и две резервные версии. Известные ключи API маскируются, однако сохранённые диалог и история содержат задачи и могут содержать текст проекта. `DEBUG` добавляет фрагменты ответов; ограничивайте доступ к состоянию и его хранению.

`current-task.json` обозначает последнюю сохранённую задачу данного каталога. Автоматическое восстановление использует указатель только при совпадении исходного проекта и наличии неприменённых файлов. Использование одного состояния для разных проектов может заменить указатель. `/resume` тоже проверяет исходный проект и сохранённый изолированный путь; чужая задача либо старый режим прямого рабочего каталога отклоняются. Используйте отдельные каталоги состояния, если нужны независимые указатели последних задач.

Восстановление после обычного выхода:

```bash
python3.8 coding_agent.py --workspace /home/user/projects/demo --state-dir /home/user/.local/state/coding-agent --model your-model-id
```

```text
/task
/diff
/apply
```

Перед `/apply` проверьте строку `Session: RESUMED (unapplied changes)` при запуске. Если прежний процесс агента ещё работает либо новая копия запущена явно, сначала выполните `/resume`. Чтобы продолжить задачу до переноса, проверьте `/task` и `/security`, затем выполните `/continue`. `/resume` восстанавливает сообщения и проверки, но самостоятельно не обращается к модели.

## 17. Рабочие сценарии

### 17.1. Функциональность Python

Укажите точную правку, поведение и ожидаемое покрытие тестами. Изучите изменённые пути, выполните компиляцию и нужные тесты, затем явно перенесите результат:

```text
Добавь --timeout с default 30 в backup.py. Проверь default и явное значение в tests/test_backup.py.
/diff
/check python_compile backup.py tests/test_backup.py
/check unittest tests
/apply
```

### 17.2. Исправление Bash

```text
Исправь кавычки в scripts/backup.sh. Сохрани текущие аргументы и коды завершения скрипта.
/check bash_syntax scripts/backup.sh
/check shellcheck scripts/backup.sh
/diff
/apply
```

При отсутствии ShellCheck сохраните сообщение `SKIPPED`. Успех синтаксиса Bash не является функциональным тестом резервного копирования.

### 17.3. Роль Ansible

```text
Исправь задачи роли nginx и добавь имена и полные имена модулей там, где нужно.
/check ansible_syntax roles/nginx
/check ansible_lint roles/nginx
/diff
/apply
```

Для синтаксиса укажите каталог роли. Обе проверки используют искусственный inventory, а не production hosts. Эти результаты не доказывают converge или идемпотентность.

### 17.4. Отказ от правок

Отклоните одну правку REVIEW клавишей Enter либо `n`. Для отмены всех изменений копии сеанса выполните `/revert`; для удаления всего сеанса и выхода — `/discard`. `/quit` сохраняет копию; при следующем запуске с теми же параметрами неприменённые правки подключатся автоматически.

## 18. Проверка реализации и архитектура

```bash
python3.8 -B coding_agent.py --self-test
```

Тесты создают временные данные внутри текущего каталога, поэтому он должен быть доступен для записи. Сервер LLM не требуется. Unit-тесты проверяют пути, правки и копии, схемы, лимиты цикла, нормализацию API, статистику, перенос рабочей копии, формирование статических команд и очистку метаданных и окружения. Реальные тесты утилит, пространств имён и ресурсов выполняются только при наличии инструментов и подтверждённой изоляции. Изучайте причины пропусков: успешный self-test не равен полному интеграционному покрытию.

В окружении проверки выпуска отсутствуют `cpu.max` пользовательской службы и `ansible-lint`; реальные интеграционные проверки пропускаются. Руководство не утверждает, что они прошли.

В [diagramms](diagramms) находятся шесть архитектурных исходников: [компоненты](diagramms/components-ru.puml), [классы](diagramms/classes-ru.puml), [жизненный цикл копии](diagramms/workspace-lifecycle-ru.puml), [последовательность изоляции](diagramms/sandbox-sequence-ru.puml), [цикл агента](diagramms/agent-loop-ru.puml) и [статические проверки](diagramms/static-validation-ru.puml). Каждый файл содержит одну диаграмму PlantUML и имеет английскую копию без `-ru`. Для просмотра используйте установленный редактор или визуализатор PlantUML; визуализация не входит в работу агента.

Docstring кода используют предложения назначения `EN:` и `RU:` и общие разделы `Args / Аргументы`, `Returns / Результат`, `Errors / Ошибки`. Описываются типы и смысл аргументов, результат и ожидаемая обработка ошибок. Комментарии на обоих языках поясняют атомарную запись, копирование относительно дескрипторов, очистку окружения, остановку процессов и приблизительный учёт контекста.

## 19. Диагностика проблем

| Признак | Действие |
| --- | --- |
| Ошибка подключения или HTTP сервера | Проверьте URL `BACKENDS`, сеть, учётные данные и процесс сервера; после правки настроек перезапустите приложение. REPL остаётся доступен. |
| `BACKEND_TIMEOUT` во время генерации модели | Проверьте указанные лимит и время. Перезапустите с большим `--llm-timeout`, затем `/resume` и `/continue`; таймаут относится к HTTP, а не к проверкам проекта. |
| Модель не найдена либо требуется выбор | Выполните `/model`, выберите реальный идентификатор и обновите `LLM_PROFILES`. |
| Ответы описывают действия, но инструменты не вызываются | Проверьте серверный шаблон или обработчик вызова функций модели; изучите `/tools`. |
| `bubblewrap ... no trusted ... executable` | Убедитесь, что утилита уже установлена, принадлежит root и находится в доверенном системном каталоге; автоматической установки нет. |
| Недоступен `cpu.max` либо другой контроллер в строгом режиме | Cgroup службы не имеет обязательного контроллера. Используйте стандартный `--sandbox portable` либо согласуйте делегирование с администратором, если нужны общие лимиты. |
| Недоступен пользовательский менеджер systemd в строгом режиме | Используйте `--sandbox portable` либо проверьте менеджер, bus и окружение, если нужен строгий режим. |
| Требуется доверенный системный Python | Запускайте системным интерпретатором внутри `/usr`, а не средой HOME/venv. |
| `SKIPPED` | Внешняя утилита отсутствует либо не является доверенной. Она не запускалась; это не PASS. |
| `INVALID_TARGET` либо нарушение пути | Укажите существующий безопасный относительный путь; для синтаксиса Ansible выберите распознанный playbook или роль. |
| Ошибка импорта pytest | pytest недоступен системному Python изоляции; `.venv` проекта не заменяет его. |
| `TIMEOUT` либо предел ресурсов | Изучите диагностику и лимиты. Проверьте проект до повышения ограниченных значений в коде. |
| `EDIT_FAILED` | Прочитайте текущий файл и выберите точный блок с одним совпадением. |
| `APPLY CONFLICT` | Оригинал изменился после записи суммы. Сравните копию и оригинал, создайте новый сеанс либо согласуйте изменения вручную; принудительного переноса нет. |
| Перенос завершился после части файлов | Изучите перечисленные пути, каталог копий и `apply.json` до восстановления. |
| Resume отклонён | Используйте тот же оригинал и состояние; удалённый или чужой сеанс нельзя подключить. |
| Неизвестен предел контекста | Задайте `--context-window` либо `context_windows` модели; оценка не является точной токенизацией. |
| Нет стрелок, TAB или истории | Используйте интерактивный терминал и Python с readline; ввод из pipe работает обычным способом. |
| Сообщён карантин | Проверьте указанную службу и каталог и подтвердите остановку до очистки; не считайте снимок удалённым. |

Оценивайте фактическую проверку по результатам разрешённых инструментов; `/apply` определяет, какие изменения копии попадут в оригинал.
